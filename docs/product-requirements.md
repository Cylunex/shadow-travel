# Shadow Travel 最终产品设计

> 状态：首版设计基线
> 更新日期：2026-08-16

## 1. 产品定位

Shadow Travel 是面向个人和少量同行人的私人旅行地图。

用户可以：

- 收藏想去的地点；
- 用主题组织公园、美食、旅行目标等点位；
- 标记自己去过的地方；
- 为一次到访添加照片和简短记录；
- 与同行人共同维护主题，但各自保存个人意愿和到访记录；
- 对需要的主题制作大致路线，并跳转高德继续导航。

一句话：

> **收藏想去的地方，标记走过的地点，把照片和记录留在地图上。**

核心关系：

> **地图是主界面，主题负责组织，地点是核心，到访保存事实，记录是可选内容。**

## 2. 产品边界

Shadow Travel 不是 Wanderlog、TripIt 一类的完整旅行规划器，也不是论坛或旅行日记平台。

首版不做：

- 机票、火车、酒店和预订；
- 费用、预算和分账；
- 小时级日程；
- 群聊、论坛和公开社区；
- 排行榜、徽章和强游戏化；
- 后台持续定位和应用内导航；
- 通用目标管理系统；
- 完整照片管理和复杂相册系统。

路线是辅助能力，不是产品核心。记录和照片需要好用，但不能取代地图与地点。

## 3. 产品原则

1. **地图优先**：主要操作从地图和地点发生。
2. **主题组织**：主题是一组有共同目的的地点，不是复杂行程。
3. **地点复用**：同一个现实地点可以加入多个主题。
4. **作用域清楚**：现实地点、主题内容、个人意愿和个人到访分别保存。
5. **记录轻量**：标记去过不强迫填写照片、文字和评分。
6. **个人独立**：同行人共同维护主题，但不能替别人修改个人到访和记录。
7. **默认私密**：个人照片和文字默认仅本人可见，主动共享后才给主题成员查看。
8. **路线可选**：没有路线的主题也必须完整可用。
9. **智能辅助**：LLM 和 Agent 负责查询、整理和生成草案，不替用户制造旅行事实。

## 4. 统一术语

产品界面使用自然中文，领域模型、API 和代码使用固定英文名称：

| 产品界面 | 领域与代码名称 |
| --- | --- |
| 主题 | TravelMap |
| 主题点位 | MapPoint |
| 现实地点 | Place |
| 个人意愿 | Preference |
| 到访 | Visit |
| 到访记录 | VisitRecord |
| 路线 | Route |

文档不再使用 Theme、ThemePoint 作为技术名称。数据库、接口、后端类型和前端类型统一围绕 TravelMap、MapPoint 命名；界面仍只向用户展示“主题”和“主题点位”。

## 5. 核心对象

首版只保留七个核心概念。

### 5.1 TravelMap（主题）

用于组织一组地点，例如：

- 北京公园年票 2026；
- 贵阳美食；
- 北京周边露营；
- 想去的博物馆。

主题包含名称、简介、封面、所有者、同行成员、地点列表、可选进度和可选路线。

首版不建立独立 Goal 实体。地点型目标只是主题的一项可选配置。

### 5.2 Place（现实地点）

Place 保存地图平台无关的地点事实：

- 名称；
- 经纬度和坐标系；
- 地址、城市和行政区；
- 高德地点 ID 等地图来源信息。

Place 不保存主题分类、标签、攻略、成员意愿、到访文字、评分和照片。同一个 Place 可以出现在多个 TravelMap 中。

### 5.3 MapPoint（主题点位）

MapPoint 表示一个 Place 在某个 TravelMap 中的主题内容。

它保存：

- 主题内显示名称；
- 分类和标签；
- 共享备注或攻略；
- 推荐菜、预约信息等主题属性；
- 排序；
- 是否计入进度。

同一家餐厅在“贵阳美食”和“五一贵州”中可以有不同的分类、备注和排序。

### 5.4 Preference（个人意愿）

Preference 属于“成员 + MapPoint”，支持：

- 未标记；
- 想去；
- 计划去；
- 暂不考虑。

“去过”不是 Preference，而是根据 Visit 判断。一个人可以已经去过某地，同时仍标记“想再去”。

### 5.5 Visit（到访）

Visit 表示某位用户到过某个 Place，保存用户、地点、到访日期、可选来源主题和可选同行人。

规则：

- 同一个地点可以有多次 Visit；
- 一键“去过”只创建 Visit；
- Visit 属于用户和地点，不属于某张主题；
- 删除主题不会删除 Visit；
- 从主题创建 Visit 时，可以通过独立的 VisitMapShare 把完成状态展示给该主题成员；
- 标记同行人不会替对方创建 Visit。

Visit 的来源与可见性必须分开：

- source_map_id 只记录从哪张 TravelMap 创建，不决定谁能看到；
- VisitMapShare 保存 Visit 对某张 TravelMap 的完成状态可见关系；
- 从主题内点击“去过”时，默认创建当前主题的 VisitMapShare，界面明确显示“同行人可看到已完成”，用户可以取消或稍后撤回；
- 从全局地图创建的 Visit 默认不创建任何 VisitMapShare；
- 本人进度读取自己的全部 Visit；查看其他成员进度时，只读取共享给当前 TravelMap 的 Visit；
- VisitMapShare 只暴露完成状态，不自动共享照片、文字或评分。

### 5.6 VisitRecord（到访记录）

VisitRecord 是一次 Visit 下可选的内容，包含简短文字、评分和多张照片。

关系保持简单：

    Place
    └─ Visit
       └─ VisitRecord（可选）
          └─ Photos

一个 Visit 首版只维护一份 VisitRecord。用户分批上传照片时，继续追加到现有 VisitRecord，不重复创建 Visit。

VisitRecord 默认私密。用户可以把整条 VisitRecord 共享给 Visit 的来源主题；首版不做同时共享到多个主题、部分照片共享和主题精选。VisitRecord 分享与 VisitMapShare 独立：共享完成状态不共享内容；共享 VisitRecord 时同时保证该主题能看到对应完成状态。

### 5.7 Route（大致路线）

Route 属于 TravelMap，由有序 MapPoint 组成。

首版只需要选择地点、拖动排序、地图连线、粗略距离和时间，以及跳转高德打开地点或导航到下一站。

不做自动最优路线、多日行程、实时交通和应用内导航。

## 6. 必须坚持的数据边界

- Place 保存现实事实；
- MapPoint 保存主题内容；
- Preference 保存个人在具体主题里的意愿；
- Visit 保存个人到访事实；
- VisitMapShare 单独保存到访完成状态对主题的可见性；
- VisitRecord 保存该次到访的照片和文字；
- Photo 不直接挂在 Place 上；
- 删除 TravelMap 或 MapPoint 不删除个人 Visit、VisitRecord 和照片。

## 7. 进度设计

主题可以关闭或开启进度。

开启后只支持两种完成方式：

- 完成全部计入进度的地点；
- 完成任意 N 个地点。

另外可以设置可选的开始和结束日期。

示例：

    北京公园年票：
    完成全部地点
    统计周期：2026-01-01 至 2026-12-31

    贵阳必吃十店：
    完成任意 10 个地点
    无统计周期

    普通贵阳美食收藏：
    不启用进度

统计规则：

- 按不同地点计数，不按 Visit 次数计数；
- 同一公园去三次，进度仍只增加一个地点；
- 有统计周期时，只计算周期内的 Visit；
- 每名成员独立计算；
- 首版不做“所有人必须一起完成”等多人目标规则。

未开启进度的主题不显示百分比，只显示地点数和想去数量。

## 8. 协作与权限

### 8.1 主题内容

- TravelMap 所有者管理主题和成员。
- 所有者和协作者可以维护 MapPoint、共享攻略和路线。
- 只读成员可以查看主题，并维护自己的 Preference、Visit 和 VisitRecord。

### 8.2 个人内容

- 每个人只能修改自己的 Preference、Visit、VisitRecord 和照片。
- 主题所有者不能删除其他成员的原始 VisitRecord 和照片。
- 个人 VisitRecord 默认私密。
- 用户可以选择将 VisitRecord 共享给当前来源主题。
- 用户撤回共享后，原始 VisitRecord 仍保留在自己的记录中。

P0 只提供当前主题下成员主动共享 VisitRecord 的简单时间列表，不做相册编排和复杂聚合。P1 再增加照片墙、按成员或地点筛选，以及更完整的共同记录浏览。

### 8.3 到访状态

从主题中标记去过时：

- 当前用户的进度立即更新；
- 可以让主题成员看到“已完成”；
- 照片和文字仍默认私密；
- 完成状态通过 VisitMapShare 独立共享；
- 是否共享 VisitRecord 由用户另外决定。

### 8.4 同行人

A 在自己的 Visit 中添加 B，只表示 A 认为 B 与自己同行：

- 不为 B 创建 Visit；
- 不修改 B 的进度；
- 不复制 A 的照片给 B。

“是否同步到我的记录”以后再做，不进入首版。

## 9. 页面与导航

一级导航：

    地图　主题　记录　我的

### 9.1 地图

- 展示用户有权访问的全部主题点位；
- 支持地图和列表切换；
- 支持主题、城市、分类、意愿和到访状态筛选；
- 同一个 Place 出现在多个主题时可以合并展示；
- 点击地点进入详情。

### 9.2 主题

- 展示主题列表、地点数和可选进度；
- 进入后查看地图和地点列表；
- 管理主题点位、共享备注和成员意愿；
- 根据配置决定是否显示路线和进度。

### 9.3 记录

- 按时间展示自己的 Visit；
- 有 VisitRecord 时直接显示照片缩略图和文字；
- 没有 VisitRecord 时显示简洁的“去过某地”事件；
- 支持按照片、主题、城市和时间筛选。

照片墙、日历、往年今日以后作为记录页内部视图，不增加一级入口。

### 9.4 我的

- 个人基础统计；
- 参与的主题和同行人；
- 导入、导出和设置；
- LLM、Agent 和隐私配置入口。

### 9.5 地点详情上下文

保留两种入口：

    /maps/:mapId/places/:placeId
    /places/:placeId

从主题进入时，可以编辑该 MapPoint 和 Preference。

从全局地图进入时，主要展示 Place 与个人 Visit；编辑主题内容前必须先选择主题。

不能通过 mapIds[0] 猜测当前主题。

## 10. 核心流程

### 10.1 添加地点

1. 在主题中搜索高德地点或地图选点。
2. 系统查找已有 Place。
3. 复用或创建 Place。
4. 创建 MapPoint。
5. 设置分类、标签、共享攻略和个人意愿。

### 10.2 一键标记去过

1. 用户点击“去过”。
2. 默认使用当天日期，也允许修改。
3. 同一地点、同一天已有 Visit 时，提示使用已有到访。
4. 创建 Visit，不强迫添加 VisitRecord。
5. 从主题进入时默认创建当前主题的 VisitMapShare，并允许用户取消。
6. VisitMapShare 只共享完成状态，不改变 VisitRecord 的私密状态。

### 10.3 添加照片和记录

1. 选择已有 Visit，或者先创建 Visit。
2. 一次选择多张照片。
3. 可选填写文字和评分。
4. 创建或更新该 Visit 的 VisitRecord。
5. 照片保存为 Shadow Media 的 media_id。
6. VisitRecord 默认私密，可选择共享给来源主题。
7. 上传失败允许重试，不能重复创建 Visit。

单次选择 9 张可以作为首版 UI 限制，但不写成永久业务规则。

### 10.4 创建路线

1. 在启用路线的主题中选择多个 MapPoint。
2. 拖动调整站点顺序。
3. 请求高德粗略路线。
4. 服务失败时仍保存顺序并画简单连线。
5. 实际出发时跳转高德。

## 11. 地图提供方

- 国内首版使用高德。
- 国际旅行预留 Google Maps。
- 必须保留 MapProvider 和前端地图适配层。
- 业务模型不能保存地图 SDK 对象或直接依赖高德接口结构。
- Place 保存平台无关地点快照，地图平台 ID 单独保存。
- 坐标必须标记 WGS84、GCJ-02 等坐标系。
- 地点搜索、详情、地理编码、粗略路线和外部跳转通过 Provider 完成。

## 12. Shadow Media

- 浏览器不持有 Media 服务凭据。
- Travel 后端负责申请上传、确认完成和获取短时访问地址。
- 业务数据库只保存 media_id。
- 不保存预签名 URL 和永久对象地址。
- 照片默认 private。
- 保留拍摄时间、位置和 EXIF 清理状态，但不默认向同行人公开 GPS。
- 删除主题不能删除个人 Visit、VisitRecord 和媒体资产。

## 13. LLM 与 Agent

LLM 和 Agent 是增强能力，不影响地图核心功能独立运行。

优先能力：

- 用自然语言筛选已有地点；
- 从文字清单中提取地点，经高德核验后生成导入草案；
- 建议分类和标签；
- 根据已确认地点和成员意愿生成路线草案；
- 后续整理用户主动选择的旧照片和记录。

规则：

- 地点、坐标和路线事实必须来自业务数据库或 MapProvider；
- 模型不能凭空创建真实地点；
- Agent 不能自动替用户标记到访；
- 写操作先生成草案，用户确认后再应用；
- 外部 Agent 使用独立 Bearer、最小 scope、幂等键和审计；
- 不信任 Agent 自报的用户身份；
- 模型统计只上报模型、Token、延迟和状态，不上传旅行内容、提示词、回答和图片 URL；
- 模型不可用时，全部手动功能正常使用。

照片整理、旅程总结和年度回顾放到后续版本，不作为首版主线。

## 14. 版本范围

### P0：先做完整闭环

1. 全局地图和主题地图。
2. 高德地点搜索、地图选点和地点详情。
3. Place 与 MapPoint 分离。
4. 主题分类、标签、共享攻略和地点排序。
5. 每名成员独立的 Preference。
6. 一键 Visit 和多次到访。
7. 一次 Visit 对应一份可选 VisitRecord。
8. 多照片上传、缩略图展示和上传重试。
9. 独立 VisitMapShare，完成状态与 VisitRecord 内容分开共享。
10. VisitRecord 私密或共享给来源主题。
11. 主题内共享 VisitRecord 的简单时间列表。
12. 地点型进度：关闭、全部、任意 N 个、可选周期。
13. 主题成员与基础角色权限。
14. 简单路线、粗略连线和跳转高德。
15. 主题、城市、分类、意愿、到访和照片筛选。
16. 北京公园年票的基础批量导入，以及基础导出。

### P1：使用体验增强

- 完整批量导入与错误修正界面；
- 共享记录照片墙、按成员或地点筛选和更完整的聚合浏览；
- 从 Shadow Media 选择已有照片；
- EXIF 建议时间和地点；
- 智能筛选和往年记录；
- 地图复制和只读分享；
- 自定义主题字段；
- 自然语言查询、地点导入草案和路线草案；
- Agent 变更预览、确认和冲突处理。

### P2：验证需求后再做

- 同行到访同步建议；
- 旧照片自动聚类；
- Journey 旅行聚合；
- 日历、往年今日和年度回顾；
- 视频和语音记录；
- 国际 Google Maps 实现；
- PWA 和有限离线浏览；
- 外部 Agent / MCP；
- 基于用户选定内容的 AI 回顾草稿。

## 15. 验收场景

### 15.1 北京公园年票

- 主题设置 2026 年有效期和“完成全部地点”。
- 用户批量加入公园。
- 往年去过不计入 2026 进度。
- 一键去过即可完成，不要求照片。
- 同一公园本年去三次，进度只增加一个，Visit 保留三次。
- 每名成员独立查看自己的进度。

### 15.2 贵阳美食

- 同一家店可以加入多个主题，各自拥有不同攻略和意愿。
- 成员共同维护美食点位，分别标记想去。
- 从想去地点建立简单路线并调整顺序。
- 到店后创建 Visit，分批上传照片时追加到同一 VisitRecord。
- 可以从地点或路线跳转高德。

### 15.3 隐私与协作

- A 标记去过并创建 VisitMapShare 后，其他成员可以看到完成状态，但看不到默认私密的照片和文字。
- A 主动共享 VisitRecord 后，主题成员才能看到内容。
- 主题所有者不能删除 A 的原始 VisitRecord。
- A 标记 B 为同行人，不改变 B 的 Visit 和进度。
- 删除主题不删除任何成员的个人 Visit 和 VisitRecord。

## 16. 开发阶段数据原则

项目仍处于开发阶段，不设计历史生产数据兼容和复杂迁移方案。

- 可以重整尚未形成正式数据基线的领域迁移；
- 开发数据库可以重建；
- 先把 Place、MapPoint、Preference、Visit、VisitMapShare、VisitRecord 和 Photo 的关系定义正确；
- 不为不存在的历史数据增加临时兼容表、双写和多阶段迁移；
- 正式产生需要保留的数据后，再只使用前向迁移。

## 17. 最终决策

- 保持地图优先，不转成完整旅行规划器或旅行日记。
- TravelMap 组织地点，目标只是 TravelMap 的轻量进度配置。
- Place 与 MapPoint 必须分开。
- Preference 属于成员和 MapPoint。
- Visit 属于用户和 Place，可以没有 VisitRecord。
- VisitMapShare 独立表达完成状态对某张 TravelMap 的可见性。
- 首版一个 Visit 只有一份可选 VisitRecord，照片可以分批追加。
- VisitRecord 默认私密，只支持简单共享给来源主题。
- 不做多主题内容分享、精选、复杂共同相册和同行确认流程。
- 进度按不同地点统计，数量规则和可选时间范围分开。
