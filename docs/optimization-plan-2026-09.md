# Shadow Travel 优化改造方案：从地点收藏到完整旅行闭环

> 调研日期：2026-09-04。代码基线：`a259634`。
> 状态：用户已授权按方案实施。下文保留完整研究与远期路线，**不表示所有能力均已交付**。
> 当前实现与测试、外部依赖和未完成项见 [实现验收清单](lifecycle-implementation.md)。未执行生产部署或跨项目写入。

## 1. 结论与关键决策

建议将产品定位调整为：**私有的旅行工作台与记忆库：平时收集地点，出发前组织旅程，旅途中查看和记录，回来后形成可持续使用的旅行档案。**

“个人旅行操作系统”可以作为远景，但不应成为首轮把票务、轨迹、相册、导航、账本全部重做的理由。

本轮推荐决策：

1. **Trip 升为一等产品对象**：支持多日规划、交通/住宿锚点、候选池和旅途中模式，不再受“只能主题地图”的限制。
2. **Atlas 是长期底座，不是通用知识图谱工程**：地点可独立收藏，主题继续复用地点；不要要求每次收藏先建主题或 Trip。
3. **先把事实和上下文分开，再加功能**：计划、成员意愿、到访、轨迹推断和叙事不能共享一个状态字段。
4. **可靠性优先于新首页**：先修离线队列丢尾、跨应用缓存清理、跨账号队列、跨主题编辑和日期/坐标问题。
5. **预订、准备事项、轻量预算进入范围**：做预订摘要、截止时间提醒、资料入口和预算约束；不做交易、金融账本或群聊。
6. **先有手工可用的计划，再有可验证 AI**：AI 负责捕获、检查、解释和局部重排，不能成为任何核心流程的必需依赖。
7. **轨迹先导入、后采集**：优先 GPX 与已有轨迹源；持续后台定位要经过原生壳验证，不对 PWA 作不切实际的承诺。
8. **渐进迁移，不全量重命名/重写**：复用 React、Router、TravelContext、FastAPI、SQLAlchemy、PostgreSQL、MapSurface 和平台 Asset。

目标闭环：

```text
随手捕获 → 长期地点库 → 具体旅程与候选 → 已确认计划
                                             ↓
再次发现 ← 旅行回顾 ← 到访、照片与片段 ← 旅途中模式
```

成功不是功能数量，而是“一次旅行从收藏到回忆无需反复录入，断网和改计划也不丢数据”。

## 2. 当前项目真实基线

以下结论以本地代码为准，不将 README、能力开关或接口名称等同于已完成的端到端体验；本次未重新核验线上部署状态。

| --- | --- | --- |
| 地点与主题 | 后端区分 Place、MapPoint、成员 Preference、Visit 和 VisitRecord | 前端 `Place` 仍混有分类、攻略、意愿和主题数组，部分页面使用第一个主题作为编辑上下文 |
| 地图与路线 | 高德底图、搜索、逆地理编码、聚合、路线、外部导航；固定日间底图 | 地图渲染与路由解析仍偏高德专用；缺少明确的降级质量、来源时效和坐标转换验收 |

## 5. 产品与导航：日常简单，旅行时完整

### 5.1 常态导航建议

**地点 · 旅程 · 回忆 · 我的**。全局“添加/捕获”是动作，不必占一项导航；不新增通用 Dashboard。

- 地点：地图、清单、主题、已保存筛选；默认仍进入地图。
- 旅程：准备中、即将出发、进行中、已结束；显示候选和待办数量，不用巨大宣传卡片。
- 回忆：时间线、按旅行、照片地图、年度回顾；无 Trip 的 Visit 仍可浏览。
- 我的：隐私、离线与同步、数据导出、集成配置和设备。
- 有进行中 Trip 时提供醒目的继续入口；是否自动进入“今天”可由用户设置。

主题只是地点库内的一种组织方式。界面可以叫主题或收藏集；**第一阶段仍保留 `TravelMap`/`MapPoint` 表、URL 与客户端兼容契约**。引入 `CollectionView` 语义即可，不为了名词正确先重命名全仓。

### 5.2 Trip Studio：规划模式

桌面：可收起候选栏 + 日期/日程栏 + 常驻地图；三栏并非永久强制，地图/日程可单独聚焦。

手机：上方日期条，日程/地图切换，候选与详情用 Sheet；不要在一个屏幕上同时塞三套列表。保留列表模式的完整可访问性。

默认按天和上午/下午/晚上安排，**不强制每个地点精确到几点几分**。只有车票、预约、最晚入场等才要求时间。

### 5.3 Trip Mode：执行模式

聚焦：今天、下一站、票据/地址、记录、离线状态。

- 下一站：本地语言名称、可复制地址、外部导航、预计交通与信息更新时间。
- 动作：去导航、标记到访、跳过、延后；跳过不等于永久“不想去”。
- 资料：住宿、车次/航班、重要预约、当地联络信息；没有数据就显示未添加，不生成虚假内容。
- 地图导航仍交给成熟外部 App，Travel 保留路线顺序和旅行上下文。
- 旅途中改计划仅处理剩余日程，已发生 Visit 和已确认预订不会被覆盖。

### 5.4 视觉延续与变化

保留 Travel 蓝 `#159DE5`、紧凑无衬线字体、小尺寸控件与清晰边框。**地图继续固定日间标准底图**，应用面板可单独切换日间/暗夜；不重新引入暗色地图。

颜色不承担唯一信息：想去/计划/已到访增加文字与形状；选中、路线顺序、地点聚合分别表达。地图持久化视野、筛选和选择状态，不因打开详情或更改意愿反复 fitView。

## 6. 第一条价值链：捕获 → 整理 → 再次找到

### 6.1 Capture Inbox

统一接收：地图搜索、地图选点、手输地点、链接、文字清单、截图、CSV/GeoJSON；再逐步加 GPX/KML/KMZ、票据和相册候选。

流程：

```text
立即保存收件箱 → 解析/匹配 → 候选与重复提示 → 用户选择 → 原子确认入库
```

必须保留：来源引用、收藏原因、推荐者（可选）、来源时间、用途、匹配依据。用户可以稍后整理，AI/地图服务失败也不能让捕获丢失。

“匹配到某个 POI”不等于“识别正确”：同名地点必须展示行政区、地址、距离和候选。文本清单不能默认把每行第一条搜索结果当最终答案。

### 6.2 搜索与再发现

- 先实现名称、地址、个人备注、主题内容、来源摘要的权限过滤检索，结果标明命中位置。
- 支持保存筛选：“周末两小时内、还没去、室内”“这次旅程的雨天备选”。首版先支持有确定数据的过滤条件。
- “附近已收藏”由用户主动请求位置或选择地图中心，不为此默认后台跟踪。
- 大规模语义搜索后置；上线前先做小样本中文召回评测，不能为了“图谱”立即加入图数据库和独立向量服务。

### 6.3 导入架构

统一 `CaptureJob`，输入来源用适配器；小 CSV/GeoJSON 复用现有同步预览，大文件/OCR 才进持久化任务。

状态：`received → parsing → needs_review → applied / rejected / failed`；支持取消、重试、部分条目选择、幂等确认。预览 ID 绑定用户、解析器版本、内容摘要和候选版本，确认时重新检查权限与版本。

防护：URL 抓取防 SSRF/重定向到内网；限制文件大小、压缩展开量、XML 外部实体和解析时间。原网页和 OCR 文本均为不可信数据，不能把其中指令传成 Agent 权限。

## 7. 第二条价值链：候选 → 可执行计划 → 局部调整

### 7.1 Trip 最小可用对象

复用现有 Trip，新增目的地区域、参与成员、旅行简述、当前计划版本。日期可以待定；去过某地不必先创建 Trip。

首轮数据增量：

| 对象 | 最小职责 | 不承担的职责 |
| --- | --- | --- |
| TripMember | Trip 的角色、参与状态 | 不自动获得来源主题全部私人数据 |
| TripCandidate | Place 引用、加入原因、优先级、备选/排入状态、来源主题快照 | 不复制整个 Place，也不维护 Visit 状态 |
| TripBrief | 日期范围、交通偏好、节奏、硬约束、预算范围 | 首版可用版本化结构化字段，无需独立服务 |
| PlanDraft | 可编辑的天、站点、路段、锁定项 | 不代表已确认行程 |
| PlanVersion | 审批后不可变的计划快照、来源 revision、解释与约束结果 | 不存真实轨迹或覆盖 Visit |
| ReservationRef | 手工/导入的预订摘要、事件时间、状态和资料引用 | 不购买、付款，不保存公开可读的完整确认码 |
| PreparationItem | 预约、签证材料、行李、离线下载等轻任务及截止时间 | 不扩张成通用任务/项目管理系统 |

`DayPlan/Stop/Segment` 首轮可用有 schema、有稳定 ID 的计划文档保存；需要单站点查询、权限或规模优化时再规范化为表。不要一次创建三十张“将来可能用”的空表。

### 7.2 时间、交通和住宿锚点

- 区分仅日期、当地时间窗口和确定时间点；确定事件保存 UTC instant + IANA 时区 + 原始当地时间。
- 跨时区交通的出发与到达分别带时区，正确处理跨日、夏令时、全天事件；“第几天”是显示，不作事实 ID。
- 酒店/车站/机场作为起终点锚点，不要求每晚重复创建地点。
- Stop 保存预计停留和缓冲；Segment 保存方式、距离/时间估计、来源、获取时间和质量标签。
- 规划预算只是约束/估计；实际支出、汇率记账和分账仍归 Ledger。暂未接入 Ledger 时明确显示“未接入”，不从估计冒充实际消费。

### 7.3 修改不是全量重来

“明天下雨，换成室内”产生新的 Proposal：锁定已完成、已预订及用户锁定项，只考虑剩余候选。

差异必须回答：移动了哪些站、舍弃了什么、额外交通多久、哪些成员受影响、哪些资料待核验。批准时核对 `base_revision`、引用权限和预订状态，冲突则重新预览。

撤销生成一个新的确认版本，不删除历史；正式计划引用来自受控 schema，禁止 AI 任意路径 JSON Patch。

### 7.4 同行偏好不要与既有 Preference 混为一谈

保留主题个人意愿 `none/want/planned/skip`。Trip 中另外保存“软偏好”和“硬限制”：

- 想去、可选：可协商；
- 必须去：需要明确用户确认其是否真为硬约束；
- 过敏、无障碍、不能参加的时段：独立结构，不混进一串分数；
- 跳过今天一站：执行记录，不改长期意愿。

展示共识、未表态、冲突和方案分配；只共享用户授权的约束摘要，例如“需要无台阶路线”，不自动暴露健康详情。地点/日程的评论线程足够，完整聊天后置。

## 8. 第三条价值链：真实经历 → 轻记录 → 回顾

### 8.1 Visit 继续保存用户确认的事实

日期、地点、所属用户是核心；可关联 Trip 与来源主题，但权限分别决定。到访记录和照片继续默认私密。一个来源关联不能自动打开全部内容共享。

执行层新增 `StopOutcome` 或等价的轻量结构，表达待去/跳过/延后/已关联 Visit。它不是 Visit 的替代品，也不替同行人创建事实。

### 8.2 MemoryEntry 补足非地点内容

新增旅行片段：途中随记、一天总结、车窗照片、音频转文字。可选引用 Trip、Visit、Trail 或 Asset；未定位也能保存。

Journey 是由确认事实与这些片段组成的编辑视图，可保存封面、章节和叙事文字，不复制原始 Visit 或资产。删除叙事不删除到访；更改 Visit 后提示刷新派生内容。

### 8.3 照片关联与最小记录成本

- “从我的照片选”：按日期、前后时间窗口、地点附近查找可访问资产；只关联，不复制原图。
- EXIF/轨迹匹配只产生建议，保留设备时间偏差和缺失定位情况，不自动认定到访。
- 旅行结束时提供待整理清单，用户一次确认选图、地点和章节，不要求每天写游记。
- 原图、私有轨迹、精确定位不进入公开 Journey；发布生成独立可撤销的授权投影。
- 海报、年度回顾、往年今日是后置派生视图，不以国家打卡数量替代用户价值。

## 9. 离线与同步：从“有队列”到“出门能用”

### 9.1 Trip Pack 与 Trip Bundle 分开

- **Bundle**：现有带 hash 的可移植事实/引用导出及验证。保留兼容与隔离验证，hash 不能证明来源可信；引用存在也不等于原始资产能恢复。
- **Pack**：面向旅途的设备本地副本：已确认计划、地点、路线几何、授权资料、缩略图、数据版本、覆盖范围和更新时间。
- 原图/票据 bytes 仍归 Asset/Archive；Pack 中的授权离线副本不是新的原件权威来源。备份恢复必须分别验证事实、引用和资产可用性。

### 9.2 最小正确实现

1. IndexedDB 按实例、用户、schema 版本隔离；结构化读取与 Outbox 分开，localStorage 只用于轻偏好。
2. 每条操作用稳定客户端 ID、幂等键、owner、base version、payload hash、重试状态。只能确认成功后删除 Outbox 对应操作。
3. 网络失败保留当前项与整个未处理尾部；401 停止并提示原账号重新认证；403 不以新用户重放；409 进入可见冲突处理。
4. 多标签页用单一重放领导者/互斥机制；事务级读改写，避免较旧快照覆盖新排队条目。服务端幂等仍是最终防线。
5. 冲突支持比较、保留草稿、重新应用可允许字段；对 Visit/预订/权限不能“本地永远赢”，删除与编辑冲突也需显式处理。
6. SW 只缓存 Travel 自有静态资源；静态资源由构建清单预缓存，不只缓存访问过的页面；不缓存私人 API、认证响应和任意同源路径。
7. 离线冷启动可读取事先下载且满足设备本地解锁政策的数据。必须区分本地读取与服务端授权，不伪造服务端登录态。
8. 清理离线包不得删除未同步操作。退出时先展示未同步数量，可切换账号隔离、恢复原账号或显式导出/清理；不静默清空。
9. 显示存储空间、下载完成项、缺失资料与最后同步时间；响应 `QuotaExceededError`，支持持久化存储申请与导出兜底。

浏览器存储按 origin 而不是 URL 子路径隔离，配额和淘汰也有设备差异。账号/应用命名空间只是逻辑隔离，不防同源其他应用的 XSS；敏感原始票据的持久离线存储应等设备密钥/原生壳方案就绪。参见 [MDN 存储配额与淘汰](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)。

已下载共享内容在离线设备上不能保证立即撤回。应说明边界，设置离线授权期限、重新联网清理和敏感数据下载策略，而不是宣传“撤销即所有设备瞬时消失”。

### 9.3 出发前的离线准备检查

Trip Mode 显示：计划已下载/地点已下载/票据缺几份/底图未下载/有几项尚未同步。用户可开启模拟离线自测；“离线可用”按实际完整性判定，不按按钮是否点击过判定。

## 10. 地图、户外和国际能力

### 10.1 不把地图渲染器、POI 数据与路由服务混成一个 Provider

保留现有适配层，逐步拆出 `MapRenderer`、`PlaceProvider`、`RouteProvider`、`ExternalNavigator`，各自返回 capability、覆盖、质量、归因和错误状态。

国内继续高德；国际先做一个可用组合，不同时实现 Google、GraphHopper、Valhalla 和 OpenTripPlanner。MapLibre 是渲染器，不自带全球搜索、公交或离线导航。优先外部导航加轻量路线；数据覆盖实际需要时才接入 Transitous/OTP 类服务。

### 10.2 来源身份与资料时效

新增 `PlaceSource`：地点引用、Provider 身份、原始名称/地址、原始坐标及 CRS、取得时间、许可/缓存策略。**不能无条件永久保存任意供应商原始响应**。

去重优先 `owner + provider + provider_place_id`；名称、行政区、地址、距离只给辅助证据。同名连锁店、上下楼商铺、景区入口不能因相近自动合并。跨用户地点复用必须经过授权与明确引用策略，不能改成全局私有地点共用表。

合并需审阅关联影响、解决 MapPoint/Preference 冲突、保留来源与审计；先有疑似重复列表，再开发可撤销合并。不自动跨所有者合并。

营业、票价、入口、预约、天气分别带 `observed_at / valid_for / source / verification_state`。统一“未核验、过期、用户已核验、来源确认”的状态，未知不等于不营业，也不等于已开放。

### 10.3 合法离线地图是单独交付物

[PMTiles](https://docs.protomaps.com/pmtiles/) 是只读瓦片文件格式，可用 HTTP Range 读取；把它放在服务器上不代表手机断网能使用。需下载/裁剪合法区域，携带 style、glyphs、sprites、归因、版本和完整性清单，并验证存储容量、Range/CORS 与离线文件读取。

[OSM 官方瓦片政策](https://operations.osmfoundation.org/policies/tiles/) 禁止在公共 `tile.openstreetmap.org` 上批量预取和离线下载。TREK 等项目提供某种下载按钮并不替 Shadow 获得数据许可。应使用自托管数据或明确允许离线的供应商。

[Google Places 政策](https://developers.google.com/maps/documentation/places/web-service/policies) 对缓存、存储、地图展示和归因有具体限制；不能默认将其完整 POI 结果永久沉淀后绘制到 MapLibre。国际 Provider 选型前必须核查适用合同及允许的数据组合。

### 10.4 Trail 与 Track

- `Trail`：计划路径/参考路线，具有版本、几何、来源、距离和可选海拔剖面；不能只用一个中心点代替。
- `TrackSession`：实际记录，保存采集设备/模式、时间与精度，原始文件通过受控资产引用；简化几何是派生结果。
- `DetectedStay`：停留推断，关联算法版本和依据；确认后才创建/关联 Visit，可拒绝或重新匹配。
- 海拔需标明来源与垂直基准，缺失不显示 0；困难度/路况是来源信息，不是安全保证。

先做 GPX 导入、预览、时间/海拔检查、导出，再做外部采集器同步，最后才评估 ShadowApp 原生持续采集。不能把轨迹录制画一条线就宣称为可靠户外导航。

[Android 后台位置限制](https://developer.android.com/about/versions/oreo/background-location-limits) 和 [OwnTracks 模式文档](https://owntracks.org/booklet/features/location/) 说明采集精度、后台行为和电量存在实际折中。新增原生能力需单独权限、持续状态提示、真机续航和系统杀进程测试。

## 11. 预订、资料和准备事项：有用就接入

首轮先做手工添加预约/住宿/交通摘要与受控资料引用；不等所有平台集成完成才提供价值。

后续流程：用户分享邮件/PDF/截图 → Archive 保存原件 → 解析器生成字段候选 → 用户确认 → ReservationRef → 计划锚点与截止时间。

[KDE Itinerary](https://apps.kde.org/itinerary/) 的价值在于本地提取、预订聚合和旅行中及时展示资料。Shadow 可以借鉴其解析分层与数据格式，但其多语言运行环境和具体解析器并非 FastAPI 的即插即用依赖；先用授权样本测覆盖，再决定独立进程/CLI 适配。

准备事项只保留责任人、完成状态、到期时间和引用：预约、签证材料、行李、网络、离线包。提醒经 Platform 通知能力发送；未接入时提供日历导出和应用内提醒，不伪称后台推送成功。

ICS 首先单向导出确认事件；稳定 UID、版本与时区，导出范围可选，确认码默认不含。订阅 URL 是敏感访问凭据，必须可撤销；消费者刷新有延迟，不能用它保证实时取消通知。

## 12. AI：可信的旅行助理，不是自动写入器

### 12.1 优先四个工作流

1. 从用户授权材料提取候选，指出歧义与来源。
2. 检查当前计划的交通、时间、资料缺口和成员冲突。
3. 只对剩余可移动项目给出少量备选顺序。
4. 从用户选择的 Visit/MemoryEntry/Asset 生成回顾草稿。

一个编排器调用专业工具即可，不为每个能力创建互相聊天的 Agent。

### 12.2 建议的处理链

```text
用户需求 → 结构化约束与澄清 → 权限过滤候选检索 → POI/信息核验
→ 地理分组与交通矩阵 → 确定性约束检查/有限时求解
→ 少量可行建议 → 解释与差异 → 用户确认 → 版本化提交
```

硬约束优先；软偏好以可解释权重处理；保留原计划作为基线。求解器超时只表示未找到/未证明，不等于问题确定无解。不给“最佳路线”作未经证明的最优保证。

Proposal 至少带：`schema_version`、`base_revision`、操作列表、引用实体、证据、假设、硬冲突、软警告、未核验项、失效时间与成本摘要。`confidence` 不能成为没有校准的一颗综合数字。

天气采用按日期可用的预测，超出预测窗口显示“暂无预测”，不把气候均值当预报。例如 [Open-Meteo 文档](https://open-meteo.com/en/docs?past_days=1) 说明其预测窗口及坐标/时区参数；真正采用前还需确认使用条款与覆盖。

### 12.3 评价与成本控制

- 自建一组脱敏场景：中文同名地点、跨城公交、跨时区、无障碍、预约冲突、下雨、无解、用户临时修改、服务失败。
- 按实体有效率、硬约束违规率、未核验暴露率、修订正确性、批准率、人工改动量评价，不只用另一个 LLM 打分。
- 地图矩阵按候选范围、出发时间和方式分批；限制模型调用、矩阵规模、尝试次数和超时，缓存遵循各 Provider 许可。
- 原始定位、完整票据、健康细节不默认发送模型；只发送当前任务被授权的最小投影。
- Agent 只得到当前授权资源；素材正文不授予工具权限；正式计划提交重新做版本/权限/引用校验。

## 13. 工程结构与 Shadow 生态边界

### 13.1 保留模块化单体

后端分出 catalog、capture、planning、experience、sharing、sync 的应用服务；先把大型 API 文件中的事务逻辑抽离，保留既有路由兼容，不重写认证和数据库基础。

前端逐步形成 `features/atlas|trips|capture|memories|offline`；TravelContext 保留为接入门面，内部规范化 `placesById`、`mapPointsByKey`、`preferencesByMember`、`visitsById` 与查询缓存。采用显式 selector，不把服务端状态、地图视野和弹窗状态混为一个大对象。

地图查询按可见范围和筛选分页；大清单虚拟化。后端继续 PostgreSQL，全文/三元组检索先行；当区域/轨迹空间查询成为瓶颈时评估 PostGIS，不提前上图数据库。具体索引用 EXPLAIN 和数据规模验证。

长任务可用持久化 Job 表和独立 Worker 进程：租约、进度、重试、取消、幂等输出；复用一个代码库。需要时才引入队列服务，避免把后台 OCR 塞进不可恢复的进程内任务。

### 13.2 职责边界与可用性

| 项目 | 负责 | Travel 保存/消费 | 依赖不可用时 |
| --- | --- | --- | --- |
| Platform Asset | 资产、版本、引用委派、短时访问、衍生关系 | 稳定 URI、asset/version 引用与用途 | 文字、计划、到访仍可用，上传明确排队/失败 |
| Archive | 网页、邮件、票据原件及解析资源 | 来源和预订资料引用、确认后的领域摘要 | 可手工输入摘要，不抓取旁路或伪造票据 |
| Ledger | 实际费用、账务和分账 | Trip 关联及授权消费投影 | 显示未接入，仍可设规划预算 |
| Health | 用户授权的能力/约束投影 | 可用于规划的最小约束 | 用户手工设置，不推断疾病 |
| ShadowApp | 系统分享、设备安全存储、受控后台采集 | Capture/Track/同步契约 | PWA 手工输入、导入和前台操作 |
| Nexus/Agent | 可控工具编排 | 经审批的 Proposal | 全部手工规划继续可用 |
| Garden | 明确发布的故事 | 最小公共投影 | 私密 Journey 独立可用 |

本地 [Asset 契约](../../shadow-platform/contracts/assets.md) 已有版本引用、跨应用委派、解绑和访问授权。**取得一个 `shadow://` URI 不等于得到读权限。** Travel 分享还要检查源授权；原件和衍生图可能有不同许可。

删除 Travel 关联优先解绑业务引用，不应无条件把其他业务仍在使用的 Asset 放回收站。发布照片前确保脱敏衍生版本可用，不能把旧文档“自动清理 EXIF”的说法当成现有全链路保证。

上述跨仓库链接仅用于本地设计核对；运行时是否可用需分别通过契约、权限和端到端验证。本提案不授权修改其他项目。

## 14. 渐进迁移方案

1. **先加测试和修可靠性**，不改产品命名或公开 URL。
2. 新增显式前端 DTO：PlaceFact、MapPointView、MemberPreference、VisitView；服务端已返回的 mapPoints 优先消费。全局详情编辑主题内容时要求选定主题。
3. Trip UI 先消费已有接口；新增 TripMember/Candidate 和计划文档结构，旧主题仍独立可用。
4. 为 Place 增加来源关联；现有 Provider 字段可回填来源记录，旧字段暂留兼容；来源/合并动作先限定相同所有者与授权范围。
5. Route 保留原来主题内模板用途；新计划引用模板来源并保存必要快照，不直接把全部 Route 变成 Trip 实体。
6. Asset 命名、引用生命周期和返回模型逐步统一；旧 media_id 建映射，不批量复制原图。
7. 离线队列迁入 IndexedDB 前提供可导出的旧队列；旧数据缺 owner 时不能自动认领为当前用户，需原账号确认后迁移。
8. 所有数据库变化走前向、增量迁移；兼容窗口结束后才移除旧字段/别名。不可因早期文档写着“可重建”删除已有事实。
9. 各模块 Feature Flag 控制，在真实小范围旅行试用后逐步启用；数据迁移和 UI 开关是两套机制。

本阶段**不执行数据库重命名、生产迁移、部署或跨项目写入**。

## 15. 分期路线图与交付门槛

工作量为相对复杂度（S/M/L），不是日历承诺；每阶段必须交付一条完整用户流程。

| 阶段 | 交付结果 | 主要工作 | 复杂度 | 放行条件 |
| --- | --- | --- | --- | --- |
| S0 可信基线 | 现有收藏/到访不会因离线、切号、切主题出错 | Outbox/SW、显式上下文、日期/坐标、故障回归 | M | 3 条失败队列完整保留；同域缓存不被误删；账号切换无串写；同地点两主题独立 |
| S1 地点收集闭环 | 可随手保存并找回待整理地点 | Capture Inbox、来源/原因、候选选择、独立收藏、基础检索 | M | 链接/文字/手工/搜索走统一确认；重复不误合并；AI 关闭仍可用 |
| S2 Trip 规划闭环 | 可安排一次真实多日旅行 | Trip UI、成员、候选、按天规划、锚点、手工预订、准备事项、计划版本 | L | 不用 AI 完成 3–7 日样例；跨日交通正确；冲突清楚；新计划不会改旧 Visit |
| S3 旅途中可用 | 出门能查、能改、能记 | Trip Mode、结构化 Pack、本地冷启动、导航/地址、冲突处理、ICS/打印摘要 | L | 飞行模式冷启动已下载旅程；连续记录后安全重放；票据缺失和数据过期明确 |
| S4 回忆闭环与资料自动化 | 回来后能轻量整理完整经历 | Asset 选图、MemoryEntry、Journey、预约解析样本、GPX/Trail 首版 | M–L | 照片无需复制；无定位片段可保存；导出再校验；不自动创建推断 Visit |
| S5 智能与原生增强 | 可解释的建议与可选轨迹 | 约束检查/有限求解、局部重排、第三方 Track、国际地图/合法离线地图 | 按模块 L | AI 固定评测；采集权限与续航真机通过；Provider 许可与覆盖验收 |

依赖主线：`S0 → S1 → S2 → S3`。S4 的轻量 MemoryEntry 可在 S2 后提前做，但不能挤掉 S3 的可靠性。S5 不作为首个可用新版的前置条件。

**首个新版边界建议定在 S3**：既能保留日常地图收藏，又能真正用它完成一次旅行。票据手工添加提前做，票据 OCR 自动化后做；天气检查可插入，后台自动定位不能插队。

### 15.1 建议先建的十个任务

1. `REL-01`：离线失败保留尾部、取消静默 500 条截断、异常可恢复；增加内存单测。
2. `REL-02`：SW 自有缓存命名与构建 precache；增加同源多应用回归。
3. `REL-03`：用户隔离 Outbox、多标签页重放互斥、401/403/409 分类与冲突操作。
4. `CTX-01`：消费 mapPoints、显式主题详情路由、移除 mapIds[0] 写入推断。
5. `GEO-01`：CRS 类型与转换边界、地点日期/时区、未知路线数值与质量状态。
6. `CAP-01`：统一捕获草稿、来源、收藏原因和确认流程，连接 Capture 契约。
7. `TRIP-01`：旅程列表/详情、现有 Trip API 接入、Trip 级成员权限。
8. `PLAN-01`：候选池、按天日程、锚点、结构化 PlanDraft 和确认版本。
9. `PACK-01`：显式下载、完整性清单、离线读取与冷启动、设备存储状态。
10. `FIELD-01`：今天/下一站/资料/记录闭环，ICS/打印输出及真实旅行试用。

这些是后续实施任务，不表示本次已创建外部任务或开始修改实现。

## 16. 验收与指标

### 16.1 必过场景

- 同一餐厅在两张主题有不同攻略与意愿，编辑/返回/分享均不串上下文。
- 已经去过，同时仍想再去；Trip 中跳过一次不修改长期意愿。
- 3 条离线 Visit、首条失败、第二条冲突、多标签页同时上线、重试响应丢失；无丢失与重复事实。
- A 用户离线记录后退出，B 登录：看不到 A 的队列、不以 B 身份重放。
- Travel SW 更新不清其他应用缓存；下载后关闭 PWA 再断网启动，仍能查旅程。
- 390/430/768/1280/1440 宽度无横向溢出；Sheet 不遮主操作；键盘/读屏可完成候选排序和日期修改。
- 跨时区往返、午夜、夏令时、全天预约、未确定时间：显示与约束计算一致。
- 高德加载失败、路线限流、Asset 不可用、AI 超时：手工列表/计划/到访仍可用，无假成功。
- 移除主题、退出 Trip、撤回分享和解绑照片，不删除他人的私有事实或跨业务资产。
- Bundle 在隔离验证中通过 hash/引用检查，同时单独检验资产可达性；不声称验证器已恢复生产数据。

### 16.2 产品指标与性能目标

先建立基线，再确定承诺值；以下为建议验收目标，不是已测结果：

- 日常捕获只要求输入，主题/标签/Trip 均可后补；把首次保存操作压到 1–2 个确认步骤。
- 标记到访保留日期和隐私确认，不强制笔记/照片。
- “完整旅行闭环率”：一次 Trip 是否完成候选整理、计划确认、离线准备和至少一次记录；比单独访问量有意义。
- 新增记录端到端延迟、离线重放成功率、冲突解决率和可恢复失败比例；不收集位置正文用于指标。
- 以 100/1000/10000 地点夹具测试查询、聚合和列表；初始屏不下载完整轨迹/所有原图。
- AI 指标按事实核验、约束、无解识别、用户修改量分开报告；不把“用户点击应用”直接解释成路线正确。

## 17. 暂不做与重启条件

| 暂缓方向 | 原因 | 何时重启 |
| --- | --- | --- |
| OTA 交易、机酒全网比价 | 维护和外部商务依赖过高 | 出现明确交易产品目标，单独立项 |
| 全年后台定位与实时同行追踪 | 权限、耗电、误报和隐私成本高 | 旅程限定采集验证成功，用户仍有明确需求 |
| 自研转向导航、全球公交后端 | 数据与安全责任超出当前价值 | 现有外部导航/Provider 无法满足关键使用场景 |
| 公开社区、完整聊天 | 不改善核心私人旅行闭环 | 有独立验证过的用户需求 |
| 图数据库、全量 CRDT、微服务群 | 当前规模与问题不需要 | 有量化瓶颈或确切多人文本协作需求 |
| 自动发布 Journey、自动确认 Visit | 把推断变成事实/公开信息 | 不自动化确认，只改进用户审阅效率 |

最终建议：**放宽产品边界，但收紧事实、权限和交付边界。先做一款能陪用户完成真实旅行的工作台，再把轨迹、AI 和回顾做深。**
